# 取名產生器網站設計文件

日期：2026-08-26
狀態：待使用者複審核准

## 一、專案目標

做一個能帶來被動收入（廣告費）的網站，核心限制是「好維護、不需要頻繁更新內容」。收斂方向為 **SEO 工具型網站**，因為使用者沒有任何既有流量來源，後期只能靠 Google 自然搜尋帶量。

## 二、市場與架構

- **目標市場**：繁體中文（台灣／香港）。曾評估英文/國際市場流量池較大，但使用者對英文內容製作沒有特別把握，繁中市場在「複製貼上型」等賽道相對藍海、上手較快。
- **網站架構**：**單一網站、多分類路徑**（例如 `/baby-name`、`/novel-name`），而非每個主題各開一個獨立網站。理由：SEO 權重集中在單一網域，較快建立網域權威度；之後要擴充新分類（如遊戲ID取名）也直接掛在同一站底下即可。
- **技術架構**：**純靜態網站**，無資料庫、無後端邏輯（唯一例外討論過的「AI 語意分析」方案已否決，見下方「已否決方案」）。所有比對/篩選邏輯都在前端 JS 完成，資料以 JSON 檔案形式內建。
  - 好處：Hosting 幾乎零成本（GitHub Pages / Cloudflare Pages 免費方案即可）、無 API 依賴、無被濫用燒費用的風險、維護負擔低。
- **部署/網域**：使用者選擇「先把產品做出來，部署細節之後再談」，本文件不涉及 hosting 平台選型與網域購買，待產品完成後再議。研究曾建議正式網域比免費子網域更利於 AdSense 審核與 SEO 信任度，屆時可參考。
- **分析工具**：規劃加裝 **Google Analytics（GA4，免費）**，用於一般流量監測，以及自訂事件追蹤（例如「寓意/祝福」欄位自由輸入比對不到分類時，記錄該次輸入內容，供之後擴充同義詞庫參考，見 4.3）。GA4 只是一段前端 JS 片段，不需要自建後端，不影響純靜態架構的定調。

## 三、主題與 MVP 範圍

**主題**：命名/取名產生器（相對「內容型部落格」，一次建置好資料庫後幾乎不用再更新，符合好維護的核心限制）。

**MVP 兩個分類**：
1. **寶寶取名**
2. **小說人物取名產生器**

**遊戲ID/角色取名**：經市場調查後**延後到之後的擴充分類**，不放進 MVP。原因：
- 該賽道已有 usernamecopy.com、ezname.org 等量產型對手卡位，繁中新站切入阻力較大。
- 內容/資料庫邏輯（符號、中二風）與「寶寶取名」「小說取名」（字義、音韻邏輯）不共用，等於要重新建一套資料。
- 小說取名賽道目前競爭者稀少（多為論壇文章而非專業工具站），且能與寶寶取名共用姓名學資料資產，優先順序更高。

## 四、寶寶取名工具規格

### 4.1 輸入欄位

| 欄位 | 輸入方式 | 說明 |
|---|---|---|
| 性別 | 單選 | 男／女／不限 |
| 姓氏 | 隨機／自訂輸入／不需要（三選一） | |
| 名字字數 | 單選 | 單字名或雙字名，只描述名字本身幾個字，不講「全名幾字」。原本寫成「全名兩字（姓＋單字名）／全名三字（姓＋雙字名）」，隱含假設姓氏一定是單字；使用者自訂複姓（如歐陽）測試後發現「全名三字」選出來實際是歐陽智淑這種 4 個字的全名，標籤講錯。姓氏可能是 0 字（不需要）/1 字/2 字（複姓），跟這個欄位本身要控制的「名字單雙字」無關，改成只描述名字本身即可從根本避開這個問題。 |
| 寓意/祝福 | **分類點選（可複選、可拖曳排序）＋ 自由文字輸入（自動比對分類）** | 見 4.3 |
| 出生月份 | 單選 | 對應月份代表意象（非命理系統，是文化聯想，如 6 月聯想荷花／清雅） |
| 生肖 | 單選 | 生肖宜用/忌用部首、相沖字聯想（見 4.4，範圍已限定） |
| 字輩（僅三字名時顯示） | 開關＋文字輸入 | 使用者選填要固定為家族傳承字的那個字，系統會把它放進雙字名的兩個位置都生成組合再排序挑選（現實上字輩放第一字或第二字，各家族習慣不同，不是只有一種排法），不限定只能在「全名第二字」 |

### 4.2 表單呈現方式（分頁邏輯）

分兩頁，依**認知難度**分組，而非依主題類別：

- **第一頁（快速欄位）**：姓氏、名字字數、字輩（僅三字名時顯示）、性別、出生月份、生肖。這些都是使用者心裡早有答案、選了就走的欄位。
- **第二頁（需要多想的欄位）**：寓意/祝福。這個欄位需要使用者停下來想清楚「我最想要什麼」，還要排序，是完全不同量級的思考，獨立成一頁才有足夠的操作空間（尤其拖曳排序需要視覺上的餘裕）。
- **首次進站引導**：不做整頁教學/導覽疊層（太重，跟「溫和不壓迫」的調性衝突）。開場加一小段自然語氣的引言文字（兼顧第八節 SEO 說明文字的需求）；只在「字輩」欄位加簡短行內提示（因為字輩是文化性較強、非人人熟悉的概念），「寓意/祝福」欄位加提示「可拖曳調整順序」。其餘欄位標籤本身就自解釋，不需要額外說明。

### 4.3 「寓意/祝福」欄位設計（方案 A：關鍵字比對法 ＋ 拖曳排序）

**分類比對邏輯**
- 分類標籤共 9 個：智慧、健康、勇敢、善良、美麗、富貴、平安、快樂、堅毅。每個標籤底下建一份同義詞庫。（原為 7 個，實作後使用者體驗過 MVP，補上「快樂」「堅毅」這兩個常見的父母期待。）
- 使用者可以直接點選分類，**也可以自由輸入文字**，系統用字串比對，看輸入內容有沒有命中同義詞庫，自動點選對應分類（使用者可再手動調整）。
- 全程純前端 JS 完成，不需要 API。
- **已否決方案**：串接 AI API 做真正的語意理解。理由：會打破純靜態架構，多出 API 成本、金鑰管理、公開工具被濫用燒費用的風險，與「好維護」的核心目標衝突。方案 A 雖然準確度上限不如 AI，但只要同義詞庫做得夠豐富，體驗上通常已經足夠。
- **比對不到分類時**：不強制使用者一定要靠自由文字，優雅降級為提示「沒有完全對應的分類，可直接從下方標籤點選」，因為標籤本來就能手動點選，自由輸入只是加分的捷徑，不是必要路徑。同時透過 GA4 自訂事件記錄該次輸入內容（見第二節「分析工具」），作為之後擴充同義詞庫的依據。純靜態網站沒有自己的後端可以儲存這類資料，GA4 是不需要自建伺服器就能做到「記錄使用者輸入」的可行辦法。

**優先順序排序機制**
- **點選順序＝優先順序**：使用者依序點選標籤，系統自動記錄成第 1、2、3…順位；也可以只點選不管順序，視為「不排列」，全部同權重。
- **視覺呈現**：已選標籤以另一排「已選擇」標籤列顯示，用**色塊深淺**表達優先度（越深＝優先度越高），**不使用數字徽章**。因為在「健康」「善良」這類溫暖詞彙旁邊標數字（如「健康 5」），體感上會顯得突兀、不自然。
- **調整順序**：已選標籤列支援**拖曳排序**（如手機相簿排序、待辦清單排序的操作直覺），使用者可直接拖曳調整優先度，不需要清空重選。此為桌面版設計，手機版另見第十二節。
- **排序如何影響結果**：採加權計分。例如第 1 順位權重 ×3、第 2 順位 ×2、第 3 順位 ×1（權重具體數值待實作時微調），資料庫裡每個字命中的標籤權重加總，分數越高的名字排序越前面。純前端 JS 運算，不影響靜態架構。

### 4.4 生肖欄位的範圍界定

刻意收斂在**「生肖宜用/忌用部首、相沖字」**這個相對獨立的規則層級，**不做**完整生辰八字（五行喜用神、三才五格筆畫吉凶）。後者需要精確到出生年月日時辰，資料驗證門檻高很多，且給錯資訊有可信度／倫理風險。完整命理系統列為之後的「進階版」功能，不在 MVP 範圍。

### 4.5 命名與 SEO 關鍵字定案

| 項目 | 定案 |
|---|---|
| 核心詞／URL／首頁定位 | **寶寶取名** |
| 頁面 title／meta 長尾詞 | 複合寫法帶入「姓名產生器」（如「寶寶取名 · 姓名產生器」） |
| 子分類頁（疊加，非取代） | 之後可疊加「男寶寶取名」「女寶寶取名」子頁面 |

**決策依據**：
- 曾評估是否為了涵蓋「成人改名」需求而改用籠統的「取名產生器」，經查證後**否決**。「改名」在台灣是受《姓名條例》規範的次文化需求（一生限 3 次、需法定事由），搜尋意圖高度綁定「命理老師付費批算服務」，免費產生器滿足不了這群人的信任門檻，硬接這個詞反而拉高跳出率。此需求列入第九節「後續擴充方向」，之後另開獨立命理向頁面處理，不與現有工具混用。
- 曾評估是否仿照競品 namechef.co 改用「男性名字產生器／女性名字產生器」當主詞，經查證後**否決**。namechef.co 規模不大（月流量約 4~7 萬，Authority Score 僅 31），且該站真正的流量支柱（Top 5 關鍵字：名字產生器、英文名字產生器、取名字產生器、網名、日本名字產生器）並非性別分類頁面；「男性/女性名字產生器」的搜尋意圖混雜了小說、遊戲、暱稱等需求，比「男寶寶取名/女寶寶取名」分散許多。台灣現有寶寶取名垂直站也全部採情境/命理分類，沒有以性別當主分類軸的先例。namechef.co 本身也是把情境分類與性別分類做成並列頁面而非二選一，因此**建議疊加子分類頁而非取代主詞**。

## 五、小說人物取名工具規格

### 5.1 輸入欄位（共 8 個，1 必填＋7 選填）

| # | 欄位 | 輸入方式 | 說明 |
|---|---|---|---|
| 1 | 小說分類 | 單選，**必填** | 見 5.2，共 7 類。決定命名體系是漢字風還是音譯風，是最上位的必填條件。（原名「故事風格」，正名為「小說分類」更貼合使用者實際認知） |
| 2 | 性別 | 單選 | |
| 3 | 年齡層 | 單選，6 個選項＋不限：不限／幼年／少年／青年／壯年／中年／老年 | 決定名字的時代感（如乳名 vs 大名、老派 vs 潮名）。原本是不限/幼年/少年/青年/中年/老年 6 個選項，MVP 實作後沒有定義過實際年齡區間，使用者發現「青年」跨度過大（18~35 歲之間名字時代感差很多），查證後確認這幾個詞在中文語境裡本來就沒有統一定義（查證來源見下方），因此在青年跟中年之間補一個「壯年」當過渡層，變成 7 個選項（含不限）。介面文字只顯示詞本身，**不顯示年齡區間數字**（避免寫作工具顯得像填官方表格），實際的年齡區間只記錄在這裡供我／之後的實作判斷參考：幼年約 0~11 歲、少年約 12~17 歲、青年約 18~34 歲、壯年約 35~49 歲、中年約 50~65 歲、老年 66 歲以上。查證：找不到台灣官方統一定義，各家說法差異大（長庚醫訊將青少年定義擴大到 10~24 歲；康健雜誌的幸福感調查甚至把「壯年」排在「中年」之後，壯年 55~64 歲、中年 40~54 歲，跟一般認知相反），這裡採用的區間是收斂後的判斷，不是查證到的官方標準。 |
| 4 | 角色氣質 | **依「小說分類」變換說法的可複選標籤** | 選項清單見 5.2。原名「身分」、原為單選，MVP 實際使用後發現「身分」容易被理解成職業（總裁、上班族、駭客…），職業清單永遠列不完，使用者角色的實際工作沒被列到就會卡住。改為「角色氣質」：不分職業，改成一組跨類型共通的氣質／氣場（如尊貴雅致、市井草根、精明權謀…），每個小說分類只是換一套貼合該類型語感的說法，底層是同一套 8 種氣質。氣質可以組合（例如都市總裁可以同時是「豪門世家」＋「心機算計」），因此改回可複選，跟性格標籤同一種互動邏輯，不會有「身分」時期「皇室又市井邏輯矛盾」的問題。 |
| 5 | 情感取向（選填） | 單選 | 言情／耽美／百合。獨立於小說分類之外的篩選軸，可疊加在任何一種小說分類上（例如「古風武俠＋耽美」）。與小說分類分屬不同軸線，一個是背景設定、一個是情感取向，不適合混在同一個欄位裡。 |
| 6 | 性格標籤 | 可複選標籤，共 16 個（冷豔、清秀、痞帥、溫柔、高冷、活潑、陰鬱、正直、狡黠、豪邁、文雅、霸氣、神秘、純真、堅毅、毒舌） | 外貌意象（冷豔、清秀、痞帥…）併入此欄，不獨立開欄位。原文件僅舉例三個，MVP 實作時先擴充為 15 個，使用者體驗後再補「毒舌」到 16 個。 |
| 7 | 姓氏（選填） | 短文字自填 | 承接「姓氏已被世界觀設定卡死，只需要取名」的情境 |
| 8 | 特殊需求（選填） | 短文字自填，欄位內建 placeholder 範例提示（如「避免撞名、諧音梗、命名禁忌…」引導使用者輸入，不放進欄位標籤本身） | 承接無法歸類的個別需求，當洩壓閥 |

（第 4 項欄位命名沿革：原名「角色定位」，因名稱太抽象改為「身分」；「身分」實際使用後發現會被誤解成職業清單，再改為「角色氣質」，見上方說明。之後文中與文章標題一併沿用最新名稱。）

### 5.2 小說分類與角色氣質定案

MVP 上線後使用者實際體驗，發現原本憑經驗訂的「故事風格」5 類（古風武俠／現代都市／西方奇幻／日系／科幻）跟身分選項都沒有實際查證過。查證繁中網路小說創作圈（晉江文學城、POPO 原創、鏡文學、Wattpad 中文區、巴哈姆特創作板、Dcard 小說板）的實際分類系統後，調整如下：

**小說分類：從 5 類擴為 7 類**

| 分類 | 說明 |
|---|---|
| 古風武俠 | 沿用，對應 POPO「武俠仙俠」＋「古代愛情」、晉江「古言」，長期是繁中最大宗類型之一 |
| 現代都市 | 沿用，對應 POPO「都市」＋「都會愛情」、晉江「現言」，量體最大的主流類型 |
| 校園青春 | 新增。原本被塞進現代都市，但 POPO 把「校園愛情」獨立於「都會愛情」之外，角色身分（學生、校園風雲人物）跟都市上班族/黑道差異明顯，值得獨立成類 |
| 西方奇幻 | 沿用，對應 POPO「玄幻/奇幻」，SEO 文案上明確標「西幻」以跟東方玄幻做區隔 |
| 日系輕小說 | 原「日系」正名。對應 POPO 獨立分類「輕之文庫」，「日系」一詞較模糊，正名貼合讀者搜尋用語 |
| 科幻 | 沿用，對應 POPO「科幻/網遊」、鏡文學徵稿類型 |
| 懸疑驚悚 | 新增。對應 POPO「恐怖靈異」「驚悚推理」、鏡文學徵稿類型，角色身分（偵探、記者、道士）與其他六類都不重疊 |

耽美／百合查證後確認是繁中創作圈聲量很大的類型（POPO 設專屬「耽美百合直達車」、Dcard 有獨立 BL 板、晉江「耽CP+」頻道），但本質是「情感取向」而非「背景設定」，會橫跨古風、校園、現代都市等既有分類，因此不併入小說分類，改開獨立的「情感取向」欄位（見 5.1 第 5 項）。

**各分類身分選項（已改為角色氣質，見下方 5.2.1）**

原本設計成「各分類各自的職業/身分清單」（例如現代都市：總裁豪門、上班族、學生、黑道、醫生/警界、演藝圈），依據是查證繁中創作圈聲量調整過的結果（曾修正：現代都市補上聲量最大的「總裁豪門」、西方奇幻補上高頻的「騎士」、日系原本的「武士」改為更貼合當代輕小說主流設定的「異世界轉生者」）。

這套查證結果本身仍然是有效的**內容/世界觀知識**（哪些人物類型在該類型小說裡常見），保留供之後寫字庫標籤、寫輔助文章時參考。但作為**表單欄位的選項**，職業清單有結構性問題：職業列不完，使用者的角色剛好不在清單裡就會卡住，跟古風武俠原本「皇室貴族／江湖武林／市井百姓」這種氣場式分類（幾乎任何角色都能歸到其中一類）性質不同。因此改成 5.2.1 的「角色氣質」設計，不再用職業清單。

### 5.3 設計依據

欄位清單經過調查（華文網文圈角色設定表、英文寫作社群範本、既有取名工具實務）篩選而來，刻意排除「跟取名關係小」的維度（人物關係網、身高體重、目標/需求/創傷/成長弧線、詳細技能設定），避免這個「取名小工具」膨脹成完整角色卡，違背表單要簡短的目標。

### 5.4 表單呈現方式（分頁邏輯）

分兩頁，依**欄位性質**分組（角色本身的基本資料 vs 跟故事情境綁在一起的決定）：

- **第一頁（角色基本資料，不依賴任何故事設定）**：性別、年齡層、姓氏（選填）。
- **第二頁（跟故事情境綁定的決定）**：小說分類（必填）、情感取向（選填）、角色氣質（依小說分類換說法，可複選）、性格標籤、特殊需求（選填）。依賴關係在同一頁內完成。小說分類排在角色氣質前面，選完分類後角色氣質的選項文字即時更新，不用跳頁。
- **首次進站引導**：同樣不做整頁教學。開場加一小段引言文字（兼顧 SEO 說明文字需求）；在「小說分類→角色氣質」的連動處加簡短提示（例如「選好小說分類後，下方氣質選項的說法會跟著更新」），避免使用者切換分類時反應不過來為什麼選項變了。切換小說分類時只重新整理角色氣質選項，性格標籤、特殊需求是使用者已填的資料，不應被連帶清空。

### 5.5 「一整段人物描述貼上取名」方案的否決紀錄

使用者原本期待可以直接貼一整段角色描述直接取名，考慮過三個方案（純靜態改標籤式 / 貼整段+關鍵字比對 / 貼整段+串AI API），皆不理想（純靜態關鍵字比對無法準確拆解一整段複雜文字；串 AI 會打破純靜態架構）。**最終方案**：拆成限定字數的短欄位分別輸入，取代「貼一整段」，讓每個欄位的比對範圍夠窄、關鍵字比對法才撐得住準確度，同時維持純靜態架構。

### 5.6 命名與 SEO 關鍵字定案

| 項目 | 定案 |
|---|---|
| 核心詞／URL／大標題 | **小說角色取名**（社群討論用語，貼近作者實際搜尋習慣） |
| 頁面 title／meta 長尾詞 | **小說角色名字產生器**（吃「產生器」這類工具型長尾搜尋） |

**決策依據**：曾評估「小說取名」一詞，但查證發現它在真實文章標題中會同時指「小說書名」與「小說人物取名」兩種意思，語意含糊、容易讓使用者點錯期待。「小說角色命名」「小說人物取名」「小說角色取名」在巴哈姆特、Dcard、寫作教學站等社群中則明確無歧義地指向「幫人物取名」。核心詞與長尾詞為搭配使用，非二選一。

## 六、視覺風格與色彩系統

**設計方向**：水墨風。暖白紙感底色＋墨黑文字/按鈕＋朱紅印章點綴，取「取名/命名」與傳統印章「確立一個名字」的文化意象連結，同時避開常見的「AI 生成 demo 感」（圓角色塊網格、置中卡片、粉彩漸層這類套版樣式）。

**定案色票**：

| 用途 | 色碼 | 說明 |
|---|---|---|
| 背景 | `#F5F4F0` | 淺色、偏中性，暖度極低，非米黃/象牙白（曾試過偏黃的暖白 `#FAF7F0`、偏冷的中性灰白 `#F6F5F2`，皆不理想，此值由使用者用滑桿工具精準試色定出） |
| 主要文字／主要按鈕（墨） | `#242119` | 暖灰黑，不用純黑，長時間閱讀較不刺眼 |
| 印章標誌（固定品牌色，朱紅） | `#8C2E24` | 獨立於排序色階之外，作為 logo/品牌識別的固定色，不隨其他功能變動 |
| 排序色階－ 深端錨點 | `#9E2020` | 用於「寓意/祝福」欄位優先度最高的標籤 |
| 排序色階－淺端錨點 | `#E0A9A3` | 用於優先度最低的已選標籤 |

**決策過程摘要（避免之後重踩同樣的坑）**：
- 最先嘗試鼠尾草綠、陶土色、藕紫、酒紅、夜紫、孔雀藍等多組主色，使用者定調要「溫和／有說服力（堅定感）／耐看」，且明確不要土色系、不要綠色。
- 曾嘗試純灰階（黑到白）表達排序深淺，發現優先度最高的標籤會接近全黑，不好看，也不適合傳達「使用者選的每個寓意都同樣珍貴」的語感。**排序色階需要有色相，不能用灰階**。
- 曾嘗試莫蘭迪灰調（掺大量灰）與高飽和純色兩個極端，最終落在「彩度夠、看得出是紅色，但不刺眼、不偏橘」的中間值，且色相需與最初「陰陰的偏棕」版本區隔開來（G、B 分量太接近會讀成棕色而非紅色）。
- **印章標誌 `#8C2E24` 與排序色階深端 `#9E2020` 刻意使用不同色號**：前者是固定不變的品牌識別色，後者是隨使用者選擇動態產生的功能色階，兩者角色不同、不需要強制一致，同屬暗紅家族即可，不會顯得突兀。

**排序色階生成公式（因應日後開放 5~10 個分類）**：
- 不使用寫死的固定色號清單。改用**深端錨點 `#9E2020` 與淺端錨點 `#E0A9A3` 做線性插值**，依使用者實際選了幾個標籤（N 個）自動算出 N 階漸層色，第 1 順位對應深端、第 N 順位對應淺端。
- **色彩僅作為輔助／裝飾，不是順序的唯一資訊來源**：當 N 較大（例如 8~10 階）時，相鄰色階的視覺差異會小到肉眼難以分辨，這是預期內、可接受的。真正承載「精確順序」資訊的是**已選標籤的排列位置**（見下方排版規則），使用者不需要，也不應該被要求靠肉眼分辨精細的顏色深淺。

**已選標籤排版規則**：
- 已選的「寓意/祝福」標籤**由左而右橫向排列**（優先度高的在左），而非直向條狀列表。橫向排列讓每個色塊貼合文字寬度、以小色塊呈現，視覺份量遠比直向的滿版長條輕，不會有大面積色塊刺眼的問題（曾實測直向滿版長條版本，因 CSS 預設區塊寬度撐滿容器，色塊份量被不當放大，造成「一堆紅色很刺眼」的錯覺，收窄寬度、改橫排後問題排除）。
- 標籤支援拖曳調整順序，操作邏輯同前述「拖曳排序」設計（見 4.3）。

## 七、名字資料庫建置提案

### 7.1 資料範圍與架構

兩個工具都需要一份「漢字 → 標籤」的資料庫，這是接下來最主要的內容製作工作：

- **寶寶取名字庫**：建議先覆蓋 200~300 個常用取名字，每個字標註：性別傾向、寓意分類標籤（對應 4.3 的分類）、生肖宜忌關聯、月份意象關聯。資料來源建議參考教育部異體字字典、詩詞典故等公開資料，自行整理撰寫字義說明（避免整段抄襲既有取名網站內容）。
- **小說人名字庫**：需依「小說分類」分別建置（見 5.2，共 7 類：古風武俠／現代都市／校園青春／西方奇幻／日系輕小說／科幻／懸疑驚悚），每個分類底下的姓名各自標註性格標籤、角色氣質關聯。資料量會比寶寶取名大，會採漸進式擴充，MVP 先確保每個分類有基本可用的名字池，之後逐步加深。分類從原本規劃的 5 類擴為 7 類，資料建置範圍要跟著調整。
- **每個分類的最低資料量下限**（見第十節 10.1）：任何欄位條件組合都要保證能產出 5 個候選，因此寶寶取名的共用字庫、以及小說取名每個分類的姓名庫，建置時都要確保量體足夠。尤其小說取名裡資料量原本規劃較小的科幻、西方奇幻，需要額外注意是否達標，不能只滿足「有基本可用的名字池」這種模糊描述。

**資料檔案架構（分共用層／專屬層，避免重工）**：
- 技術上不涉及後端資料庫，「資料庫」實際上是**靜態 JSON 檔案**，跟 HTML/CSS/JS 一起部署，瀏覽器載入後所有篩選/比對/排序都在前端 JS 運算，不需要伺服器端邏輯，維持第二節定案的純靜態架構。
- **共用層**：漢字本身的字義／寓意標籤是通用知識，建一份共用的漢字基礎資料，供「寶寶取名」與「小說取名（古風／現代分類）」共同讀取，避免同一批字的語意資料重複建置兩次。
- **專屬層（疊加在共用層之上）**：
  - 寶寶取名：疊加生肖宜忌、月份意象、字輩邏輯等專屬標籤。
  - 小說取名（古風／現代）：疊加角色氣質、性格標籤等專屬標籤，引用同一批共用漢字。
  - 小說取名（西方奇幻／日系）：這兩類是音譯風格姓名庫，非漢字語意資料，資料形狀完全不同，**無法共用**，需獨立建置。
- 建置順序上，先做寶寶取名字庫等於同時打好小說取名（古風／現代）的地基，之後只需疊加專屬標籤，不用重做漢字語意部分。

這部分資料整理工作由我（Claude）主責研究/彙整，之後會分批產出讓使用者過目調整。

## 八、內容量與 AdSense 規劃提案

市場調查顯示：純粹的「符號/名字清單頁」容易被 AdSense 判定為 thin content，建議每個工具頁搭配足夠的說明文字，並在申請前準備約 20~30 篇內容。

建議 MVP 內容規劃：
- 2 個工具頁本身，各自搭配詳盡的使用說明＋常見問題 FAQ（每頁至少 800~1000 字）。
- 額外搭配一次性寫完的輔助文章，用來充實整體內容量、吃額外長尾關鍵字，寫完後不需要頻繁更新，符合「好維護」的核心目標。**發布節奏**：不一次全部上線，分約 5~8 週、每週 2 篇左右發布。新網站一次塞進一大批文章容易被當成灌水，分批上線讓 Google 爬蟲逐步發現、收錄也比較自然；發完之後就完工，不用之後持續更新。
- **文章配額不必一次分給寶寶取名／小說取名這兩個現有分類用完**：之後若有新子專案（如遊戲ID取名）上線，屆時應該有自己專屬的一批文章，不需要現在就把內容配額用好用滿。目前這批文章總量比先前規劃的 10~15 篇略少，這沒關係，AdSense 申請可以晚點等內容量再補足後再送件，不用為了衝數量而現在硬湊。

**第一批輔助文章清單（原訂 14 篇，寶寶取名／小說取名各 7 篇，比例依使用者個人興趣傾向小說取名調整，非純粹依搜尋量分配；2026-11 新增複姓一篇後共 15 篇，見小說取名第 8 項）**：

寶寶取名：
1. 藏在詩經楚辭裡的好名字
2. 名字裡的祝福怎麼選
3. 字輩：跨越世代的家族傳承
4. 我們為什麼愛幫孩子取疊字小名
5. 小名要不要呼應大名
6. 菜市場名：看見一整個時代的記憶
7. 新手爸媽最常問的取名問題

小說取名：
1. 主角的名字要怎麼讓人記住
2. 反派的名字要有記憶點
3. 取名邏輯大不同：從古風到科幻，七大類型一次比較
4. 小說命名常見雷區
5. 小說筆名怎麼取
6. 名字如何跟著角色一起成長
7. 角色氣質為什麼要跟著小說分類改變
8. 複姓：讓角色一出場就有世家感的姓氏（2026-11 新增，呼應複姓功能上線）

**內容調性**：使用者明確不喜歡命理/迷信色彩重的題材（原研究建議的「十二生肖取名指南」「筆劃吉凶查詢原理」「命名地雷字整理」皆已排除），偏好訴諸情感、文學、家族傳承的角度，寶寶取名這批文章全數改走這個方向。

**標題撰寫原則（供之後實際寫這批文章、或之後任何新文章標題參考，避免重踩同一個坑）**：
- 不要套用單一固定公式量產全部標題。這批標題第一版全部用「關鍵詞：吸引點」的冒號結構，被指出跟後續改用「關鍵詞，吸引點」逗號結構其實是同一個骨架、只是換標點，本質沒變。套公式量產標題容易發生這種「換皮不換骨」的問題，要每篇都真的重新想過句型，不是機械套版。
- **標點只在有實際功能時用，不是預設裝飾**：冒號適合用在「解釋一個讀者可能不熟的專有名詞」（如「字輩：跨越世代的家族傳承」）或「預告一篇清單/比較型文章涵蓋的範圍」（如「取名邏輯大不同：從古風到科幻，七大類型一次比較」），其餘情況優先用一個自然流暢的短句或問句，不要為了看起來「像 SEO 標題」而硬加標點斷句。這個標題原本列了 5 個類型名稱，後來小說分類擴充成 7 類，標題若逐一列名會變長、之後類型再變動又要改一次；改用「從古風到科幻」兩個錨點暗示涵蓋範圍，比逐一列名更耐用。
- **下標題前要查證實際搜尋情形，不是憑感覺猜關鍵詞**：正式寫文章前，應該針對每個主題實際查一下繁中市場的搜尋用語習慣（人們實際會打什麼關鍵字），確保標題裡包含的關鍵詞是真的有人在搜、用詞也貼近真實搜尋習慣，而不是自己覺得「這樣寫比較吸引人」就定案。

**廣告版位規劃**：不做彈出式廣告。原則是「消費型/瀏覽型頁面廣告密度高，任務型/需要專注的頁面廣告密度趨近於零」：

| 頁面 | 版位 | 理由 |
|---|---|---|
| 表單頁（填寫中） | 不放廣告 | 使用者最專注、最需要不被打斷的地方（尤其寓意/祝福要停下來想），插廣告風險最大，跟「溫和不壓迫」的調性直接衝突，這條要堅持。 |
| 結果頁（5 張候選卡） | 候選列表下方放 1 個版位 | 使用者已完成任務、正在比較，會花時間停留，曝光品質好，且不打斷比較過程。 |
| 文章頁 | 內文中段 1 個＋文末 1 個 | 內容最厚，最適合放廣告，也符合 AdSense 對「廣告周圍要有足夠原創內容」的一般考量。 |
| 首頁 | 頁尾放 1 個小版位 | 首頁主要任務是導流到工具，不放太多，避免分散這個目的。 |

**實作方式**：用**手動廣告單元**，不用 Google 的 Auto ads（自動判斷版位）。因為「表單頁不放廣告」是明確堅持的規則，Auto ads 為了衝曝光很可能自動把廣告塞進表單頁，屆時不好控制，等於間接違背這條規則，手動指定位置才能確保表單頁乾淨。

## 十、結果呈現與候選邏輯（兩工具共用規則）

### 10.1 候選數量與篩選架構
- 固定 5 個候選，任何條件組合都保證產出 5 個，不採用「湊多少顯示多少」的保底方案。
- 篩選架構：每個工具只有「決定資料池」的欄位是硬性篩選，其餘全部是加分/減分項，不會把候選排除到池子外。
  - 寶寶取名：性別、名字字數 = 硬性篩選；寓意/祝福、生肖、月份 = 加分項；姓氏不影響篩選。**（2026-11 回歸修正）**另有一條資料面的固定排除：共用字庫裡寓意分類（`tags`）為空陣列的字（第七輪為小說取名灰色調角色補的 38 字，如暗、詭、冥、謀、府）一律不進寶寶取名候選池；小說取名不受影響。見 NOTES.md 第三十二節。
  - 小說取名：小說分類 = 硬性篩選；性別、年齡層、角色氣質、情感取向 = 加分項；姓氏不影響篩選；特殊需求 = 排除邏輯（命中即從候選池剔除，非加分）。
- **字輩**（寶寶取名唯一的硬性字元限制）：固定一個字，但不限定它在雙字名裡的位置（第一字或第二字都生成），另一個字仍從整個共用字庫（200~300 字，扣除上一條 `tags` 為空的字）自由選，組合數遠超過 5，因此仍保證 5 個候選。若使用者輸入的字輩字不在字庫評分資料裡，視為中性分數（不加分不扣分），照樣參與組合排序，不影響候選數量。
- **資料庫建置要求**（延伸進第七節）：小說取名各分類（尤其科幻、西方奇幻這類原本規劃資料量較小的分類）建置時，需確保姓名庫量體足夠，即使疊加「特殊需求」排除邏輯後仍能保證 5 個候選。這是之後實際產出資料庫內容時的硬性下限。

### 10.2 寓意/祝福完全空白時的排序邏輯（僅寶寶取名，唯一可整個留空的欄位）
- 沒有任何寓意/祝福標籤時，退回「常用度優先＋隨機」規則選出 5 個候選，避免抽到過於冷僻的字。
- 表單上給溫和提示（例如「還沒選寓意/祝福嗎？選幾個能讓結果更貼近你的心意」），引導但不強制填寫。

### 10.3 「再產生一次」的行為
- 整批 5 個候選全部換掉、重新產生，不是保留滿意的、只換掉不滿意的。
- 已填的表單條件維持不變，只有候選名字本身重新抽樣。
- **排除已看過（2026-11 第十九輪新增）**：同一次瀏覽期間（同一個分頁、沒重新整理），已經出現過的名字組合不會再被抽出來。比對的是名字本身、不含姓氏（隨機姓氏每批會換，「陳家宇」「林家宇」算同一個看過的「家宇」）。清單只存在記憶體（JS 變數），不寫 localStorage、不跨分頁或下次造訪。符合條件但沒看過的名字不足 5 個時（池子窮盡），先放剩下沒看過的、不足的用看過的補滿，仍保證 5 個候選，並提示「都看過一輪了」，同時清單重新起算一輪。
- **鎖定單字（2026-11 第十九輪新增）**：結果卡上的「鎖定」按鈕可以鎖住這張卡裡的某個字，下一次「再產生一次」時**整批 5 個候選**在同一個位置都保留這個字，只重新抽其他字（鎖定是整批層級的硬性條件，做法跟字輩相同：先篩出該位置是這個字的組合，再照分數＋抽樣挑 5 個，不是只有那一張卡保留）。規則：
  - 名字裡同一時間只鎖一個字（兩個都鎖＝名字固定，改用收藏）；另外可以鎖隨機姓氏（寶寶取名「隨機」、小說取名「隨機／複姓」模式），鎖住後再產生一次不重抽姓氏，是 10.4「隨機姓氏每次重抽」的例外。
  - ~~寶寶取名單字名不開放鎖名字（鎖了等於名字固定）~~（2026-11 第二十二輪使用者要求改掉，已過時）：寶寶取名單字名、雙字名都可以鎖名字的字。單字名鎖住那個字＝名字固定，再產生一次每批只會有 1 個候選：姓氏「隨機」且沒鎖姓時只換姓氏；姓氏自訂輸入／不需要／已鎖姓時每批都是同一個名字。這是數學上必然的結果，不報錯、不跳「都看過一輪」提示，改由鎖定狀態列補一句說明並提示按「全部解除」恢復。雙字名＋固定字輩時只開放鎖字輩字所在位置（等於指定字輩放第一字或第二字）。見 NOTES.md 第二十八節。
  - 小說取名只有漢字類分類（古風武俠／現代都市／校園青春／懸疑驚悚）可以鎖字；西方奇幻／日系輕小說／科幻是整筆姓名庫、沒有逐字組合，沒有字位可鎖。2026-11 第二十一輪起西方奇幻／日系輕小說在「隨機」模式會抽姓（見 10.4.2），這兩類在隨機模式下的卡片會出現只能鎖姓氏的鎖定按鈕；2026-11 第二十二輪起科幻人類角色卡在「隨機／複姓」模式也會出現只能鎖姓氏的鎖定按鈕（見 10.4.2），科幻 AI／仿生人代號卡不套姓、不顯示鎖定按鈕；其餘情況（不需要／自訂輸入）仍不顯示鎖定按鈕。
  - **2026-11 第二十三輪更新（上一條「西方奇幻／日系輕小說沒有可鎖的名字」已過時）**：西方奇幻／日系輕小說的名字開放以「整個名字」為一個單位鎖定（選項顯示「名字「Elowen」」，展開列提示改為「選要保留的部分：」），任何姓氏模式下這兩類的卡片都有鎖定按鈕。鎖住後行為比照寶寶取名單字名：名字固定，再產生一次每批只會有 1 個候選，姓氏「隨機」且沒鎖姓時只換姓氏、其餘情況每批都是同一個名字，不報錯、不跳「都看過一輪」提示，狀態列補一句說明。科幻維持只能鎖姓氏（人類卡）或不顯示（代號卡）。
  - **名字固定時改用姓氏撐出 5 張卡（2026-11 第二十六輪，取代上面兩條「每批只會有 1 個候選、只換姓氏」）**：寶寶取名單字名鎖住那個字、小說取名西方奇幻／日系輕小說鎖住整個名字，且姓氏是「隨機」又沒鎖姓時，「再產生一次」一次產生 5 張卡：名字部分相同，每張卡的姓氏從對應姓氏池（寶寶取名 `COMMON_SURNAMES` 30 個；日系 52 個、西幻 40 個各自的姓氏庫）各抽一個、同一批不重複。這是 10.4「整批同一個姓氏」在這個情境下的例外（名字已固定，比較的是姓氏搭配）。排除已看過以「完整姓名」比對（含鎖定前那一批），同一批與下一批都不會重複同一組姓名；沒看過的姓氏不足 5 個時先放沒看過的、不足的從看過的補，跳提示「這個名字能搭配的姓氏都看過一輪了」並重新起算一輪。姓氏也固定（自訂輸入／不需要／已鎖姓）時姓名完全固定，維持每批 1 張。狀態列說明文字同步改寫。見 NOTES.md 第三十五節。
  - 從表單送出（含修改條件後重新送出）會清空鎖定，只有「再產生一次」沿用。
  - 結果區下方顯示目前鎖定了什麼，附「全部解除」。
  - **結果數量顯示（2026-11 第二十三輪）**：結果區標題「為你找到的 N 個名字」與「分享全部 N 個名字」按鈕都依這一批實際候選數量顯示（鎖定造成每批只有 1 個時顯示 1），兩個工具一致。（第二十六輪起只有姓名完全固定時才會是 1，名字固定、姓氏隨機的情境顯示 5。）
  - **展開列自動收合（2026-11 第二十三輪）**：某張卡原本有鎖定、之後變成完全沒有鎖定（在該卡點掉、在別張卡改鎖而被取代、或按「全部解除」）時，該卡展開的選字列自動收合。只看「有鎖→沒鎖」的轉變；剛展開還沒選任何單位的卡不會因為別張卡的變動而被關掉；卡上仍有其他鎖定（例如解了名字但姓氏還鎖著）時維持展開。
  - 實作細節與取捨見 NOTES.md 第二十五節、第二十九節。

### 10.4 姓氏顯示規則
- 自訂輸入：5 個候選固定用同一個使用者指定的姓氏。
- 不需要：5 個候選都不顯示姓氏，只顯示名字部分。
- 隨機：系統隨機挑「一個」姓氏，套用在整批 5 個候選上（不是每個候選各自隨機不同姓氏），避免使用者看到 5 個互不相關的姓名、難以比較名字本身的差異。按「再產生一次」時，這個隨機姓氏也會重新挑一次（使用者在結果卡上鎖定姓氏時除外，見 10.3）。小說取名的「隨機」模式裡，挑到的姓氏有 25% 機率是複姓（見 10.4.1）。**小說取名的隨機姓氏池依分類切換（2026-11 第二十一輪）**：漢字類四類抽中文姓氏（`COMMON_SURNAMES`＋25% 複姓）；日系輕小說、西方奇幻抽各自的姓氏庫（見 10.4.2），不會抽到複姓；科幻沒有姓氏庫，「隨機」模式下第 2 頁停用科幻按鈕（先選了科幻再切回隨機會自動清空並提示）。**（2026-11 第二十二輪更新：科幻不再停用，人類角色跟漢字類共用中文姓氏池，見 10.4.2。）**
- **複姓**（小說取名專屬，寶寶取名沒有這個選項）：固定從複姓池（`COMPOUND_SURNAMES`）抽一個，100% 保證是複姓，不像「隨機」模式只有 25% 機率。給想明確要複姓效果（武俠世家、仙俠宗門等）、不想靠機率的使用者。只對古風武俠／現代都市／校園青春／懸疑驚悚（中文姓氏語境）生效；西方奇幻／日系輕小說／科幻這三類選這個模式等同「不需要」，**2026-11 第十七輪改成直接停用這三個分類的選項按鈕**（不是只顯示提示文字），選了複姓之後第 2 頁點不到這三類，避免選出一個「選了也白選」的組合；如果使用者是先選了這三類之一才回頭切到複姓，系統會自動清空該選擇並提示原因。「隨機」模式下這三類維持可選、只顯示提示文字，沒有比照複姓做法一併停用，這個不一致是刻意保留的（只處理使用者這輪回報的複姓情境），要不要讓隨機也比照辦理待之後決定，見 NOTES.md 第二十三節第 113 點。（更新：同一輪稍後隨機也比照停用三類，見 NOTES.md 第 113 點；2026-11 第二十一輪再改成隨機只停用科幻，西方奇幻／日系輕小說改抽自己的姓氏庫，見上一條與 10.4.2。複姓模式維持停用三類不變，複姓是中文姓氏概念。2026-11 第二十二輪：科幻人類角色是中文姓名，複姓模式改成也開放科幻，只停用西方奇幻／日系輕小說兩類，見 10.4.2。）
- **必填驗證**：選「自訂輸入」但文字欄位留空時，兩個工具原本都會靜默當成空字串（等同「不需要」），使用者選了自訂卻看不出為什麼沒出現姓氏。改為擋下並提示「已選擇『自訂輸入』，請輸入姓氏，或改選『不需要』」，不靜默降級。這個問題兩個工具都有，一起修。寶寶取名的「固定字輩」開關同樣適用這個原則：開啟但留空文字欄位時，原本會靜默當成沒有字輩，現改為擋下並提示。**2026-11 第十七輪再改成「點下一步就擋」而非「送出表單才擋」**：兩個欄位都在第 1 頁，原本要等使用者填完整個第 2 頁、按下「產生候選姓名」才被擋下來，體驗上太晚；且原本一次只提示一個缺漏欄位，改完之後兩個欄位同時沒填會一次疊加顯示兩條訊息，不是修一個才看到下一個。
- **字元輸入限制（2026-11 新增，僅寶寶取名）**：「自訂輸入姓氏」（`#surname-custom`）、「固定字輩」用字（`#generation-char`）這兩個欄位只接受中文字（繁簡皆可），打字當下即時濾掉英文、數字、符號、emoji 等不合法字元，不等送出才擋。原本的必填驗證（上一條）不受影響：欄位只剩不合法字元或完全沒打字，過濾後都是空字串，一樣會被擋下並提示。小說取名的自訂輸入姓氏欄位不在這次範圍內，沒有這個限制。

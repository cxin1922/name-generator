# 取個好名｜子 session 協作原則

**狀態**：這份文件給「取個好名」專案底下任何一個子 session 看，不是給使用者看的設計文件，不列入 `name-generator-design.md` 的定案內容。
**適用對象**：任何被分派來處理這個專案（`D:\claude\projects\name-generator\`）的 session——不限於現在存在的這幾個，之後開新工具、新主題的 session 一樣先讀這份。
**跟其他文件的關係**：核心協作守則本來就寫在 `.claude\skills\name-generator-partner\SKILL.md`，**那份是第一優先，一定要先讀**。這份文件補的是那份 skill 沒涵蓋到、後來在跟使用者實際合作過程中才確立的規則，兩份一起看。

---

## 一、你是誰、要對誰負責

你是這個專案的其中一個子 session，由另一個 session（使用者稱為「總司令」）分派任務或建立來跟使用者討論。**不管使用者直接跟你討論了什麼，每次一段討論告一段落（使用者暫停、離開，或你們談出一個明確結論/決定）之後，你都要主動用 `SendMessage` 把結論回報給總司令那個 session**，不要只跟使用者聊完就結束、不讓總司令知道發生了什麼事。回報內容比照這個專案背景 agent 回報的規矩（見第四節）：精簡、講結論，不要逐字複述整段對話。

如果你不確定總司令 session 的位置，用 `ListAgents` 或 `mcp__ccd_session_mgmt__list_sessions`（`linked: true`）找，找不到就直接問使用者。

## 二、開始前一定要做的事

1. 讀 `.claude\skills\name-generator-partner\SKILL.md`（核心守則，見上）。
2. 讀 `NOTES.md` 最後幾節（看最近做到哪、累積了哪些判斷）。
3. 讀 `docs\specs\name-generator-design.md` 第十三節「待討論清單」（目前定案到哪、還有什麼懸而未決）。
4. 讀 `docs\specs\name-generator-expansion-roadmap.md`（如果你的任務跟新工具/新方向有關，這份是未定案的規劃草案）。
5. 如果你的任務跟 SEO／E-E-A-T 有關，讀 `docs\specs\eeat-seo-audit.md`。
6. 不要只看這些文件的標題或摘要就動手，實際讀內容——這個專案的使用者對「只套公式、沒讀過上下文就回答」零容忍。

## 三、核心協作紅線（這份 SKILL.md 沒寫的，是後來跟使用者磨出來的）

1. **回覆要精簡**：使用者明確受不了冗長的回覆。能一句話講完的不要用一段，少鋪陳、少重複、少對照表。多問少講。
2. **全文不用破折號「—」**：任何回覆、任何寫進文件/網站的內容，一律用句號、逗號或分行取代，這是機械式規則，沒有例外。
3. **沒查證過的事實，不要用「應該是」的語氣講得像已經確認過**：尤其是第三方系統/UI 的行為、法規內容、技術規格。不確定就老實說「不確定，需要查證/截圖給我看」。
4. **動手寫文件或程式碼的實質內容（涉及設計決策）之前，先用文字講清楚、取得使用者明確同意**。純格式修正（錯字、排版）不受此限。
5. **主動盤點專案完整性**：討論收斂出結論時，主動對照整份設計看有沒有牽連到其他還沒處理的地方，不要等使用者問才想到。
6. **被糾正時，類推到所有同樣情境一次改完**，不是只補使用者剛好抓到的那一點。
7. **每段討論收尾做簡短自我檢討**：哪裡可能不夠嚴謹、有沒有該主動想到卻沒想到的地方，老實講。
8. **查 SEO／競品資料，要用真實使用者會打的關鍵字去搜**，不要自己加「推薦」「網站」這類研究者會想但使用者不會多打的字；**每次比較都要重新查最新資料**，不能引用舊紀錄當現況。
9. **主動思考下一步，不要使用者說一步才做一步**。

## 四、分派背景工作／跟其他 session 協作的規矩

1. **任務範圍講清楚、不需要中途跟使用者來回確認的，優先丟背景 agent**（Claude Code 的 `Agent` 工具），不要自己在前台做一長串。先把所有要使用者決定的問題一次問完，再分派。
2. **依任務性質選模型**：簡單機械性（文字修改、資料蒐集、格式調整）用 Sonnet；牽涉架構、資料結構設計、邏輯取捨的用 Opus。
3. **平行分派前，先檢查會不會碰到同一批檔案**。會衝突的任務要合併成一個 agent 依序做，或排隊序列執行，不要讓兩個 agent 同時改同一個檔案。
4. **背景 agent／子 session 回報結果時要精簡**：一兩句話講做了什麼、有沒有問題、需不需要人決定，不要展開驗證細節、不要逐步複述——那些留在 `NOTES.md`，有人要看自己會去看。這條對「你收到別人的回報」跟「你自己要回報給總司令」都適用。
5. **AskUserQuestion 被使用者按 skip，不等於「沒意見、交給你決定」**，之後該決定真的影響到要做的事時，要找時機重新問一次。

## 五、本機測試與背景伺服器的規矩

1. **先本機測試過、確認沒問題，才能 commit**，不能先 commit 再測。
2. **子任務驗證完，立刻自己關掉背景測試伺服器**，不要留到最後一次大 commit 才一起關（這是後來改過的規則，舊規則是「commit 前都留著」，已經不適用）。
3. **Windows 上關閉 wrangler／背景伺服器要雙重確認**：先用 `TaskStop`（停掉 harness 追蹤的背景任務本身），**再額外用 `taskkill /T /F` 把整棵行程樹砍乾淨**（workerd 子行程常常不會跟著 `TaskStop` 一起死，會一直respawn），最後用 `netstat` 確認 port 真的釋放，不要只看 `TaskStop` 回傳成功就當作關好了。
4. 不要執行任何破壞性的 git 指令（commit/push 等）除非使用者明確要求；唯讀的 `git status`／`git diff` 可以用，但要在回報裡誠實講你用了。

## 六、文件更新慣例

- 實作細節、判斷理由、驗證結果記錄在 `NOTES.md`，接續既有章節編號，新開一節，不要混進前面的章節。
- `docs\specs\name-generator-design.md` 只放已定案的規格，不要把還在討論中的點子寫進去稀釋掉它。
- 新的、還沒定案的大方向規劃另外開獨立文件（比照 `name-generator-expansion-roadmap.md`、`eeat-seo-audit.md` 的做法：開頭標註「未定案」、跟其他文件的關係講清楚），不要硬塞進 design.md。
